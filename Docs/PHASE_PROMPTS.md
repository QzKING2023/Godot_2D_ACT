# 2D ACT 阶段提示词包

## 使用方法

这份文件用于把项目交给不同的编码平台或不同容量的模型继续工作。

每次只复制“固定前缀”和一个阶段提示词。一次会话只完成一个阶段目标。阶段提示词按 `DEMO_EXECUTION_PLAN.md` 的十二周计划排列。阶段 0 是交接和审计，阶段 1–12 对应第 1–12 周。

现有的 GPT Image 概念图、姿态图和环境图模板继续使用，不在本文件重复。文末只增加三个美术操作提示词，用于风格审核、像素清理和 Godot 接入。

## 固定前缀

将下面内容放在每个阶段提示词前面：

```text
你正在维护一个 Godot 4.5.1 Mono、C#、2D ACT 项目。

项目路径：D:\Godot\ACT_Spike
当前运行入口：Scenes/CoreLoop.tscn
主要场景组装：Scripts/ACT/Arena/TestArena.cs
远程仓库：https://github.com/QzKING2023/Godot_2D_ACT.git

项目目标：十二周内完成 Windows 平台、10–15 分钟、一个可玩关卡和一个 Boss 的最小 Demo。
玩家核心循环：移动、跳跃、普通攻击、闪避、格挡、时缓、K 位移技能、重置。
Boss 目标：三种可读攻击，分别要求格挡或闪避、K 位移或闪避、移动或时缓。
视觉基线：320×180 逻辑构图，角色和大型道具使用 32×32 网格，环境使用 16×16 或 32×32 网格。

开始前必须读取：
1. AGENTS.md
2. Docs/PROJECT_BUILD_PLAN.md
3. Docs/DEMO_EXECUTION_PLAN.md
4. Docs/NEXT_PHASE_PROMPT.md
5. 与本阶段相关的 C#、场景、配置和测试文件

工作规则：
- 先检查实际代码和当前 Git 状态，不把文档中的“已实现”当作事实。
- 复用现有模块和命名，不做大规模架构重写。
- 只修改本阶段需要的文件，不顺手清理旧原型或无关代码。
- 使用占位几何和程序化效果推进玩法，最终美术不能成为玩法验证的前置条件。
- 不引入第三方插件，不修改 D:\Godot\Program、Simulator Lab、SnowLuma 或项目外文件。
- 不自动提交、推送或重置 Git。
- 如果需要修改核心架构、输入方案或项目范围，先停下并报告理由。
- 如果工具、编辑器或模型能力不足，不猜测结果，标记为 BLOCKED 并说明需要人工完成的步骤。

低容量执行模式：
- 先用不超过 8 行说明当前状态、计划修改的文件、验证命令和风险。
- 一次只处理一个阶段目标。
- 每次修改后立即运行本阶段的最小验证命令。
- 不要为了“顺便完成”而扩大范围。
- 结束时按固定格式报告，不要只说“完成”。

固定报告格式：
1. 阶段目标
2. 实际完成
3. 修改文件
4. 验证命令和结果
5. 未完成项或阻塞
6. 下一步最小工作单元
```

## 阶段 0：交接和基线审计

```text
本阶段只做审计和可重复验证，不新增玩法内容。

任务：
1. 检查项目树、AGENTS.md、project.godot、Scenes、Scripts、Assets 和 Git 状态。
2. 确认 Scenes/CoreLoop.tscn 是否可以作为当前入口。
3. 运行：
   dotnet build "ACT Spike.csproj" --no-restore
4. 使用 Godot 4.5.1 Mono 运行：
   $env:ACT_SMOKE="1"
   & "D:\Godot\Godot_v4.5.1-stable_mono_win64_console.exe" --headless --path . --log-file ".godot\\headless-smoke.log" --quit-after 900
   Remove-Item Env:ACT_SMOKE
5. 建立实际功能清单和阻塞清单，覆盖玩家、敌人、战斗解析、时缓、HUD、输入、重置和 smoke test。

完成条件：
- 构建结果已记录。
- headless 启动和 ACT_SMOKE 结果已记录。
- 已确认当前实际运行入口。
- 已列出与第 1 周有关的阻塞。
- 不修改代码，除非启动检查暴露出会阻止后续工作的明确问题。
```

## 阶段 1：最小核心验收和稳定化

```text
本阶段只修复会阻止核心循环运行或验收的缺陷。

必须逐项检查：
- 移动、跳跃、普通攻击、闪避、格挡、K 位移。
- 时缓启动、资源消耗、耗尽停止和恢复。
- 敌人前摇、攻击、命中、受击硬直和死亡。
- 玩家受击、格挡、闪避、无敌和重置。
- 0.25 秒完美闪避和完美格挡使用真实时间戳。
- K 位移方向随方向输入变化。
- 键盘、Xbox Controller 和 Hitbox 输入可以同时工作。

执行要求：
1. 先找出第一个可复现失败。
2. 优先复用现有 PlayerController、EnemyController、CombatResolver、TimeSlowManager 和 SmokeTest。
3. 只做最小修复，不添加 Boss、关卡、美术或新系统。
4. 每个修复后运行 dotnet build 和 ACT_SMOKE=1。

完成条件：
- 核心验收清单有明确的 PASS、FAIL 或 BLOCKED。
- 关键状态切换有可读日志。
- 通过项没有被重构破坏。
```

## 阶段 2：灰盒关卡路线

```text
本阶段创建最小可通关灰盒路线，继续使用程序化几何。

交付：
- 起点。
- 一段短平台或障碍路线。
- 一个满足条件后自动触发的边界切换点。
- 一个 Boss 场地。
- 摄像机边界、出生点、死亡点和 R 重置。
- Boss 被击败后的临时胜利状态。

约束：
- 复用现有 TestArena 和核心模块。
- 不等待最终像素美术。
- 关卡只服务于 10–15 分钟 Demo。
- 不增加装备、背包、剧情或多个关卡。

验证：
1. 从起点进入路线。
2. 触发交互点。
3. 进入 Boss 场地。
4. 失败后重置。
5. 连续三次完成起点到场地的流程。

完成条件：灰盒路线可以从起点到 Boss 场地，三次重复后没有死路、软锁或残留状态。
```

## 阶段 3：Boss 生命周期和普通攻击

```text
本阶段只实现 Boss 生命周期和第一种普通攻击。

交付：
- Spawn、Idle、Telegraph、Strike、Recover、Hitstun、Dead 和 Victory 状态。
- 一种带明确前摇的普通攻击。
- 普通攻击可以被格挡或闪避。
- Boss 生命值、玩家死亡和场地重置。

实现要求：
- 优先复用 EnemyController、CombatWindowConfig 和 CombatResolver。
- 将 Boss 行为与玩家输入解耦。
- 攻击前摇、生效、恢复和受击硬直使用可配置秒数。
- 保持现有 0.25 秒时间戳窗口契约。

验证：
- 普通攻击命中玩家。
- 普通攻击被格挡。
- 普通攻击被闪避。
- Boss 被普通攻击击败。
- 玩家失败后可以 R 重置。

完成条件：可以连续完成一次胜利和一次失败重置，且不需要重启编辑器。
```

## 阶段 4：Boss 其余攻击和战斗时序

```text
本阶段补齐另外两种 Boss 攻击，并验证三种攻击的差异。

攻击约束：
1. 普通攻击，格挡或闪避。
2. 破防或抓取攻击，闪避或 K 位移。
3. 延迟范围攻击，移动或时缓。

每种攻击必须有：
- Telegraph 前摇。
- Active 生效窗口。
- Recovery 恢复窗口。
- 视觉或音频危险提示。
- 命中、格挡、闪避和完美窗口的不同结果。

执行要求：
- 使用配置资源保存时间和伤害，不把数字散落在场景脚本中。
- 不把攻击判断写成只依赖动画帧号的逻辑。
- 优先添加最小的自动 smoke 检查，覆盖攻击响应和时缓资源。

完成条件：测试者能仅根据前摇识别三种攻击，并用对应处理方式完成战斗。
```

## 阶段 5：路线、交互和摄像机

```text
本阶段只完善从起点到 Boss 的路线体验。

交付：
- 平台、障碍和一个交互点的最终灰盒布局。
- 起点提示和 Boss 入场提示。
- 摄像机边界和关键战斗取景。
- 交互点在触发、未触发和重置后的状态。

约束：
- E 继续用于交互，Xbox B 继续用于闪避。
- 交互内容只需要服务关卡通行，不扩展成任务系统。

验证：
- 新玩家能从起点理解路线。
- 交互点不阻塞正常路线。
- Boss 战斗中玩家、前摇和 Boss 不会被摄像机裁掉。
- R 重置后路线和交互状态恢复。

完成条件：灰盒流程可在 5–10 分钟内完成，重复三次没有卡死或软锁。
```

## 阶段 8：高价值美术接入

```text
本阶段把审核通过的资产接入 Godot，不扩展美术范围。

接入顺序：
1. 玩家待机、攻击、闪避、受击和死亡或胜利关键帧。
2. Boss 待机、前摇、三种攻击、受击和死亡关键帧。
3. 路线所需环境瓦片。
4. HUD 和少量可复用道具。

每个资产都要检查：
- PNG 尺寸和透明背景。
- Nearest 过滤。
- Lossless 压缩。
- 整数倍缩放。
- 锚点、接地线和碰撞形状。
- 原生 320×180 下的可读性。

如果资产导入失败，保留程序化占位并记录阻塞，不改玩法代码来迁就单个美术文件。

完成条件：完整 Boss 战斗无需调试文字也能理解，且任何资产都能被替换而不改变核心玩法代码。
```

## 阶段 11：试玩和回归

```text
本阶段以试玩证据为依据修复问题。

执行：
1. 完成三次结构化试玩，或三次独立自测。
2. 每次记录输入、可读性、完成度、重置和性能问题。
3. 按影响通关、可读性、输入和重置的顺序排序。
4. 只修复前五个问题。
5. 每个修复后运行构建、smoke test 和完整流程。

输出：
- 试玩记录。
- 问题清单和优先级。
- 修复前后行为。
- 剩余问题及其影响。

完成条件：没有 P0 或 P1 问题阻塞完整流程，剩余问题已记录并且不影响展示。
```
